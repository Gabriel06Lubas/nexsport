## Key design decisions

### Two layers of roles
- `User.role` (`SUPER_ADMIN | CLUB_OWNER | STAFF | COACH | STUDENT`) is the
  platform-wide role. It goes into the Auth.js JWT and drives route-level RBAC
  in the middleware (Step 2).
- `ClubMember.role` + `ClubMember.permissions[]` is the authority *inside one
  club*. A user can coach at Club A and be a student at Club B, or be STAFF and
  COACH in the same club (one row per role, `@@unique([clubId, userId, role])`).
  `User.activeClubId` seeds `token.clubId`.

### Tenant isolation in the database
Every tenant-owned table carries `clubId`. Where a row points at another
tenant-owned row, it uses a **composite foreign key** on `(id, clubId)`, so a
session in Club A cannot reference a court or a ball machine from Club B:

```prisma
facility  Facility        @relation(fields: [facilityId, clubId], references: [id, clubId])
equipment Equipment       @relation(fields: [equipmentId, clubId], references: [id, clubId])
session   PracticeSession @relation(fields: [sessionId, clubId],   references: [id, clubId])
```

### Double-booking guards (enforced by Postgres, not just app code)
App-level "check then insert" code has a race: two coaches click "Create" at
the same moment, both checks pass, and both inserts succeed. nexport closes that
race in the database:

| Resource | Mechanism | Constraint name |
| --- | --- | --- |
| Facility (field/court) | `EXCLUDE USING gist (facilityId WITH =, tstzrange(startsAt, endsAt, '[)') WITH &&) WHERE status <> 'CANCELLED'` | `PracticeSession_facility_no_overlap` |
| Equipment (quantity-based) | `BEFORE INSERT/UPDATE` trigger: row-lock the `Equipment` row, then `SUM(quantity)` of overlapping active bookings ≤ stock | `EquipmentBooking_capacity` |
| Equipment stock reduction | Trigger refuses to lower `quantity` below peak reserved units | `EquipmentBooking_capacity` |
| Session seats | Trigger: row-lock the session, then `count(ACCEPTED) < maxParticipants` | `SessionParticipant_capacity` |

All guards raise SQLSTATE `23P01` with a stable constraint name. Step 4's
scheduling service maps that one error to a typed `BookingConflictError`.

Details:
- **Half-open ranges** (`'[)'`): 10:00–11:00 and 11:00–12:00 do not conflict.
- **Cancelled sessions free the slot**: the exclusion constraint is partial.
  Cancelling a session also releases its equipment (sync trigger).
- **Rescheduling** a session shifts its equipment bookings by the same delta
  and keeps any setup/teardown padding. Shifting re-runs the capacity guard, so
  a reschedule into a conflict fails as a whole.
- **Why a no-op `UPDATE` and not `SELECT … FOR UPDATE`** for the lock: the
  concurrency test showed that under `REPEATABLE READ`, `FOR UPDATE` only waits
  on the lock. It does not refresh the snapshot, so two transactions could
  both book the last unit. A real (no-op) `UPDATE` makes the second
  transaction fail with `40001 serialization_failure` instead. Under
  `READ COMMITTED` (Prisma's default) it re-reads the committed data and is
  rejected with `23P01`.
- **Retry `40001`.** Under `SERIALIZABLE`, Postgres may abort *both* racers
  with `40001` rather than admit both. It never lets both through. The
  scheduling service (Step 4) retries `40001` a few times, and the race test
  does the same.

### Money
- Integer minor units plus a lowercase ISO-4217 code (Stripe's convention).
  CHECKs enforce `0 ≤ applicationFeeAmount ≤ amount`,
  `0 ≤ refundedAmount ≤ amount`, and positive amounts.
- `PracticeSession.coachShareBps` and `Subscription.platformFeeBps` are basis
  points, so the fee split needs no floating-point math.
- **Separate charges and transfers**: the platform charges the student, keeps
  `applicationFeeAmount`, and records one `PaymentTransfer` per payee (club,
  coach). That is how one payment pays both a club *and* a coach, which a
  single destination charge cannot do.
- A partial unique index allows at most one live (non-failed, non-canceled)
  payment per session seat, so a retried checkout cannot charge twice.
- `appliedRefundPercent` snapshots the policy outcome on the payment, so later
  edits to a club's policy never rewrite history.

### Polymorphic ownership
`Subscription` and `StripeAccount` belong to *either* a club *or* a coach.
Instead of a `type` + untyped `ownerId`, they use two nullable real FKs plus
`CHECK (num_nonnulls(clubId, userId) = 1)`. Postgres keeps referential
integrity, and Prisma gives typed relations. `Like` (post XOR comment) uses the
same pattern.

### Social counters
`Profile.followerCount`, `Post.likeCount`, and the other counters are
denormalised for cheap feed rendering. The social service updates them in the
same transaction as the `Follow`/`Like` row, and CHECKs keep them ≥ 0.

### Why the guards live in a separate migration
Prisma's schema language has no CHECK, EXCLUDE, or trigger syntax. Prisma also
ignores these objects when diffing, so `prisma migrate dev` will not try to drop
them (verified: `prisma migrate diff --from-config-datasource --to-schema …`
reports *No difference detected*). Each guard is still noted in a comment next
to its model in `schema.prisma`.

## Running it

```bash
cp .env.example .env          # point DATABASE_URL at Postgres ≥ 14
npm install
npm run db:deploy             # apply both migrations
npm run db:generate           # generate the typed client into src/generated/prisma

# Integration tests (rolled back, leave no data behind)
psql "${DATABASE_URL%%\?*}" -v ON_ERROR_STOP=1 -f prisma/tests/booking_guards.test.sql
prisma/tests/booking_races.sh
```

For later schema changes, edit `schema.prisma`, then run
`npx prisma migrate dev --name <change>`. For a new raw-SQL guard, use
`--create-only` and append the SQL before applying.

## Verified
- `prisma validate` passes, and `prisma migrate deploy` applies both migrations
  to PostgreSQL 16.
- `booking_guards.test.sql`: 20/20 pass. Covers overlap, back-to-back,
  cross-tenant FK, time order, release on cancel, pooled vs unique equipment,
  stock reduction, reschedule shift and conflict, seat cap, and the
  polymorphic CHECKs.
- `booking_races.sh`: two concurrent transactions race for the same court, the
  last ball machine, and the last seat. Exactly one wins under `READ COMMITTED`,
  `REPEATABLE READ`, and `SERIALIZABLE`; 10/10 consecutive runs were stable.
- `tsc --strict` passes against the generated client.
